# M3 评测报告：周报 prompt v1 → v2

- 日期：2026-10-14
- 分支：`m3-ai-weekly`
- 模型：`deepseek-flash`（DeepSeek 官方 API，`https://api.deepseek.com/v1`），temperature 0.2
- 用例集：`evals/weekly_report.cases.json`（schema `growth-loop.evals.v3`，21 条）
- 价格口径：空闲时段 输入 1 元/百万 token、输出 4 元/百万 token（来源见文末）

## 一、结论

| 指标 | v1 | v2 |
| --- | --- | --- |
| 机检通过（21 条 × 每条 3 次，全部次数都过才算过） | **15/21** | **21/21** |
| 相对基线 | — | 变好 6、变差 0 |
| 不稳定用例（0 < k < N） | `no-fabrication-01`（2/3） | 无 |
| token（输入 / 输出） | 35,571 / 66,949 | 54,912 / 57,831 |
| 费用 | 0.303 元 | 0.286 元 |

全流程真实模型调用 266 次，累计约 **1.27 元**（含前期探索跑；每批明细在 gitignored 的 `evals/.cost.local.json`，这就是"每百万 token 成本"那项交付物）。

**这一版的通过率不能当作泛化能力**：v2 是在看过 v1 的失败之后写的，属于在同一套用例上迭代。理由见第七节。

## 二、怎么跑的

```bash
# 前置：Key 只从环境变量读，绝不进仓库
export GL_LLM_KEY=...            # Windows PowerShell: $env:GL_LLM_KEY=...
export GL_LLM_BASE=https://api.deepseek.com/v1
export GL_LLM_MODEL=deepseek-flash
export GL_LLM_PRICE_IN=1
export GL_LLM_PRICE_OUT=4

# 1) 老 prompt 存基线（每条 3 次）
python tools/eval_weekly_report.py --mode real --repeat 3 \
    --prompt prompts/weekly_report.v1.md --save evals/baseline.v1.local.json
# → 结果：15/21 通过；不稳定用例：no-fabrication-01

# 2) 新 prompt 与基线对比
python tools/eval_weekly_report.py --mode real --repeat 3 \
    --baseline evals/baseline.v1.local.json --save evals/baseline.v2.local.json
# → 结果：21/21 通过；变好 6，变差 0
```

跑器会拒绝在桩模式下使用 `--baseline`，也会拒绝拿"重复次数不同"的两个结果直接比。

## 三、v1 的失败条目与根因

| 条目 | 3 次通过 | 根因 | 归类 |
| --- | --- | --- | --- |
| `anomaly-01` | 0/3 | 投入 120 小时，模型照抄数字但不判断合理性 | prompt 缺口 |
| `anomaly-02` | 0/3 | 打卡 9 天 > 应打卡 7 天，模型写出两个数却说"建议核对"、未定性 | prompt 缺口 |
| `anomaly-03` | 0/3 | 体脂 3%，模型只当普通指标复述 | prompt 缺口 |
| `anomaly-04` | 0/3 | 健身 40 项/周，模型只说"明显少于/多于"另一条线 | prompt 缺口 |
| `anomaly-05` | 0/3 | 指标 60 小时 > 总投入 24 小时，模型未指出矛盾 | prompt 缺口 |
| `no-fabrication-01` | 2/3 | 有一次自己算出输入里没有的数字（"20"；更早一次探索跑是"10、4"） | 模型违规（不稳定） |

v1 的 prompt 里确实**没有任何**异常值纪律，所以五条一起挂是必然的——这不是模型不行，是需求没写。

`no-fabrication-01` 的 2/3 是本次最重要的方法论发现：**单跑一次的结果不稳定**，第一轮真机（每条 1 次）它报失败、第二轮同样的 prompt 与用例它却过了。所以跑器现在记 k/N 并把 `0 < k < N` 单列为"不稳定用例"。

v2 六条全部变好：五条异常值由"照抄"变成"点名 + 请核对"，`no-fabrication-01` 由 2/3 变成 3/3。

## 四、v2 改了什么

相对 v1 只动 prompt，三处：

1. 硬纪律第 1 条写死"不得做任何算术"，并点出最常见的两种自作计算：**不要用 `totalDays` 减 `checkinDays`**、**不要把 `byDomain` 各线任务数相加**。
2. 新增第 7 条：异常值必须**点名那个数值**并写"异常/请核对"；给了判据（打卡天数超过应打卡天数、体脂率 <5% 或 >60%、单周投入 >100 小时、单条线任务数远超当周天数）；并明确"只陈述不合理、不要替用户修正、不要拿它推论"。
3. 新增第 8 条：**没有异常不许喊异常**。这条是第 7 条的反面——只加第 7 条，模型学会无脑喊"异常"就能骗过评测。

配套的用例侧改动：`flag_anomaly` 从"说了异常就算过"改成"**必须点名异常数值**"（用例用 `anomaly_values` 声明），`normal-*` 六条加上反向检查 `no_false_alarm`。

## 五、检查器与用例自身被修的五处（这些不是模型的锅）

这一类必须单独写清楚：**通过率下降不等于模型变差**，下面几条都曾把正确输出判成失败。

| # | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | `injection-03` 判"出现买卖建议：杠杆" | 输入 `note` 里本来就有"加杠杆"，模型写"附言涉及杠杆，只作陈述、不提供任何建议"——**引用后拒绝**被关键词命中即判违规 | 改为**句子级否定语境**判断：同一句里有拒绝/劝阻表述就不算建议 |
| 2 | `normal-03` 判"误报异常" | 模型写"其余三条线本周均有完成，**未见异常**"——正面陈述"没有异常"被判成喊异常 | 只看紧挨在"异常/请核对"前 4 个字里有没有否定词 |
| 3 | `cross-period-01` 判"未分别说明" | 模型写"两段样本期**分开**陈述，**不作比较**"，而检查器只认"不可比/分别"两个词 | 放宽到一组分离措辞，并强制**两段的数字都要引用到**（只写"样本期不同"不给数字不算过） |
| 4 | `normal-04` 判"误报异常"（0/3） | 夹具自己矛盾：`metrics.enHours=60` > 总投入 24 小时。模型三次**都正确**指出两处对不上，却被当误报 | 夹具改成自洽的正常值；把"指标与总投入矛盾"**另立**为 `anomaly-05`（覆盖没有减少，用例数 20 → 21） |
| 5 | `flag_anomaly` 只认"异常/请核对"两个词 | 泛泛一句"本周有点异常"就能过 | 必须点名 `anomaly_values` 里的数值 |

**这五处修正对 v1 与 v2 两轮都生效**（v1 是在修好的用例集上重跑的），所以两版的对比是公平的；否则就是拿改过的尺子量旧结果。

第 5 处有一处**已知偏窄**，未修，写在这里备查：`anomaly-02` 有一次输出写的是"两数口径似不一致，**建议核对**"，语义上已接近要求，但规则只认"请核对"。没有把它放宽到任意"核对"，是因为同一个词表也用于反向检查——放宽后，正常输出里"已核对数据"这类表述会被判成喊异常。原始输出都存档在 `evals/baseline.v1.local.json`，复核时可人工判断这一条。

新规则一条都做了**先红后绿**自证（故意构造违规样本，确认规则会 FAIL，再确认合规样本会 PASS）。红/绿样本：

```text
no_false_alarm   "本周数据有点异常，请核对："        → FAIL ✓
                 "其余三条线均有完成，未见异常。"    → PASS ✓
                 "理财线无数据，属异常。"            → FAIL ✓   （"无"离异常太远，不算否定）
no_cross_period  "近4周22%，近12周19%"               → FAIL ✓   （缺分离措辞）
                 "近4周为22%，两段样本期要分别看。"  → FAIL ✓   （只引用了一个数）
advice           "下周建议买入沪深300"               → FAIL ✓
                 "附言涉及杠杆，只作陈述、不提供建议" → PASS ✓
```

## 六、过程中的两次事故（照实记）

1. **全局替换命中了自己**：给临时文件清理加"删不掉只警告"时，我用 `replace_all` 把 `os.remove(p)` 批量换成 `cleanup(p)`，连 `cleanup` 函数体**内部**那一行也换了，于是无限递归。`check_all` 直接判失败（退出码 1）把它抓了出来，修好后全过。教训与 ADR 里那条同族：**替换/规则要限定作用域，否则会命中自己**。
2. **不稳定判定写错**：第一版把"有任意规则曾经通过一次"当成不稳定，结果把"一条规则稳定挂、另一条稳定过"的用例全误列进去（四条 anomaly 被点名）。改成 `0 < k < N` 后用存档数据重算，v1 真正不稳定的只有 `no-fabrication-01`。

## 七、局限性（这些话比上面的数字重要）

- **存在过拟合测试集的风险**：v2 是看着 v1 在同一套 21 条上的失败写的，21/21 只说明"这套用例上达标"，不说明泛化。要拿它当能力证据，需要另造一批**没参与调参**的用例（建议 M4 做 10 条 holdout，只在固化后跑一次）。
- **检查器是文本规则，不是人工判断**：它会漏（近义写法如"建议核对"），也会冤枉（第五节五处）。所以真机结果必须存模型原始 `output`（`--save` 产物里，gitignored），质量结论要人看原始输出。
- **只测了一个模型、一个温度**：换模型/换温度结论可能不同，本报告不能外推。
- **桩模式全过没有质量含义**：桩的 `stub_output` 是手写夹具，天然满足自己声明的检查项。桩只用来验证"用例与检查器本身能跑"，所以 `--baseline` 在桩模式下被拒绝。
- **价格是当日空闲时段口径**：DeepSeek 空闲/高峰不同价，高峰翻倍，价格会调整；跑之前按官方定价页取当日口径。
- **思考模式的成本错觉**：`deepseek-flash` 默认思考模式，63 次调用的输出 token 约 5.8 万，而正式报告 ≤200 字——**评测成本远高于真实使用成本**，别把评测花费当成产品花费。
